These decisions settle research design so implementation does not wait for
additional menu choices. They do not assert that adapters, Catalog bindings,
oracles, campaigns, or the paper are complete.

1. **Keep the hash-locked matrix unchanged.** Baseline has 58 cells, default
   Scale has 60, and Artifact has 6. The two scale-extreme cells remain a
   separately registered conflict appendix.
2. **Reuse the real frozen ProvSQL data where it fits.** S1, S2, S4, and S5 use
   `provsql_orders`/`provsql_lineitem` and their existing Publications. SF1 and
   SF10 mean 5,000 and 50,000 query thresholds, not separate 50k/500k corpora.
3. **Use a real 414,000-row Exposure Product where reuse does not fit.** S3 and
   Dependency Scale use `final_v5_exposure_scale` /
   `final-v5-exposure-scale-v1`; five dependency Facts are derived per retained
   row from one base row and four predicate fields.
4. **Fix Dependency overlap as two equal-size real sets.** Candidate is
   `(0,M]`, existing is `(M-K,2M-K]`, intersection is `K`, and union is
   `2M-K` rows. In Fact units, existing=candidate=`N`, overlap=`5K`, and
   union=`2N-5K`.
5. **Separate history and candidate query identities.** History uses
   `sum(metric)` and candidate uses `count(*)`. This is the approved solution
   for a 100%-dependency-overlap novel candidate; the future adapter must
   implement and test the identity sequence before the cells are runnable.
6. **Realize x1 overlap over all 30 measured samples.** The four targets use
   0/15/27/30 overlapping memberships. x100 and x10k use exact integer
   per-sample counts. Warmups are deterministic, separately domain-separated,
   and excluded.
7. **Use the four-stage semantic View meaning.** S4 is fixed
   filter/projection, connected join, aggregate, then root projection. The
   root exposes two public terminal-scope fields in addition to the three
   analytical fields; the outer query projects only the analytical fields.
   Live PostgreSQL must generate and bind the root View contract.
8. **Use structured UNION for BDG.** S5 Direct is SQL `UNION DISTINCT`; S5 BDG
   uses SDK `execute_plan` with a two-branch structured union. Plain SQL is not
   an acceptable BDG substitute for this workload.
9. **Use sixteen real result fields.** The result-heavy x16 schema and
   deterministic formulas match the independent Result Oracle exactly; x4 is
   the leading four-field projection. The physical text collation is
   `en_US.utf8`, version `2.36`.
10. **Use one logical-result normalizer across paths.** Direct PostgreSQL,
    drained BDG rows, and read-back Parquet values use the same typed,
    length-delimited SHA-256 contract with explicit NULLs. S1/S3/S6 and
    Artifact use query order; S2/S4/S5 use a canonical typed-row lexical order
    because those frozen queries define no total result order and therefore do
    not rely on returned row order.
11. **Keep oracles independent.** Expected rows and FactSets cannot be copied
    from production output. Oracle manifests contain counts and digests, not
    credentials, sensitive rows, or raw Fact-ID lists.
12. **Treat SQL MD5 probe values as sanity checks only.** A separate
    evaluation-only typed streaming SHA-256 is the binding Dataset fingerprint.

16. **Resolve branch-qualified columns rather than restate the workload.**
    (Taken 2026-08-08, with 17; both fix what is to be built and approve no
    generated byte, campaign, capability, or paper number.)
    Baseline S5's six V5 BDG arms fail closed at preparation because
    `queryplan.PredicateBindings` keys its products by product name, so a
    branch-qualified column such as `left_branch.expense_type` resolves to
    nothing. The approved fix is the **qualified-column refactor**: predicate
    bindings become keyed by (branch role, product) and `Compile` emits
    branch-qualified column references. Restating the S5 plan to lift its
    predicates out of the branches is **rejected** — it would contradict
    decision 8, which fixes S5 BDG as a two-branch structured union and refuses
    plain-SQL substitutes; and excluding the arms is rejected because it
    narrows a claim the mechanism can in fact support. Consequences: the
    contract release may then state support for **two-branch UNION DISTINCT
    with branch-local predicates**;
    `TestUnionBranchFilteredPredicatesFailClosedUnderV5` must be inverted into a
    positive assertion; `TestTheBranchFilteredUnionDependencySetIsExactlyBaselineS5`
    must be deleted per its own instructions once the dependency set empties;
    and the parity case must be promoted from the unfiltered union form back to
    the filtered one. There must remain exactly one implementation, in
    `internal/physicalquery` — no second derivation may grow in
    `internal/gateway`.

17. **Implement the online inner equijoin.** The TKDE revision scoped Join as

    that is an author decision to re-open, **not** a licence to revert to the

18. **Prefill the whole existing FactSet, not the overlap.** (Taken
    2026-08-10, with 19; both settle P4.0 adjudications and approve no
    generated byte, campaign, capability, or paper number.)
    The Dependency Scale contract fixes existing=candidate=`N` with
    intersection `5K` and union `2N-5K` (decision 4), but the validator models
    history as the intersection itself: `validateDependencyCellBinding`
    requires `history.DependencyFacts == spec.OverlapFacts` and refuses any
    history on a zero-overlap cell, and the finalizer requires
    `RootBefore.DependencyCardinality == spec.OverlapFacts` (an empty root at
    zero overlap) and `RootAfter.DependencyCardinality == spec.CandidateFacts`.
    That is existing as a subset of candidate with union equal to candidate —
    **the exact modeling C6 already rejected**, and the half of decision 4 that
    was never implemented (`DependencyScaleSpec` carries no `ExistingFacts`
    field at all). Narrowing the contract to match the validator is
    **rejected** on three grounds: it would overturn decision 4 a second time;
    the frozen 414,000-row `final_v5_exposure_scale` Product exists only to
    hold `candidate (0,M]` beside `existing (M-K,2M-K]`, so under the
    validator's reading its second half is never written and 207,000 rows
    would have sufficed; and it confounds the experiment, because a history
    sized at the intersection makes store size a function of overlap — the
    zero-overlap cell would insert into an empty store — which systematically
    flatters the low-overlap cells in the very numbers Scale reports. The
    validator therefore moves to the contract: `DependencyScaleSpec` gains
    `ExistingFacts` (= `CandidateFacts`); **every** cell declares a history of
    `ExistingFacts`, the zero-overlap cell included, where it simply does not
    intersect the candidate; `RootBefore.DependencyCardinality` becomes
    `ExistingFacts`; and `RootAfter` becomes the union `2N-5K` under its own
    independent digest, which may no longer equal the candidate digest. The
    accounting invariant is what this preserves and must not move: charged
    `== N - 5K` and actual minus charged `== 5K`. History keeps the decision 5
    `sum(metric)` identity over `(M-K,2M-K]`, which is what stops the 100%
    cell from degenerating into semantic replay. The independent oracle
    produces three FactSet digests — existing, candidate, union — none copied
    from production output (decision 11). Consequence and timing: this changes
    measured runtime behaviour, so like decision 17 it must land **before** the
    v1.5 freeze and any P5 publication measurement; prefill volume rises from
    `5K` to `N` per cell (roughly 1.83M additional Facts across the twelve
    cells, concentrated in the zero-overlap large cell) and must be budgeted
    into P5.2. If the implementation stays inside `evaluation/` and does not
    reach `Derive`, decision 17's full `evaluation/exposure` re-run is not
    triggered; confirm that at implementation time rather than assuming it.

19. **Remove the Artifact private dependency section.** Each Artifact cell
    binding carries `dependency_facts` and `dependency_set_sha256` through the
    shared `BoundQueryExpectation`, and **nothing checks them**: the Artifact

    correct shape: it carries no dependency material and reaches V3 acceptance
    on the oracle manifest and canonical result digests alone, so this aligns
    the publication binding to a shape already proven sufficient. Consequences:

    material, or the Artifact branch must require `dependency_facts == 0` with

    observations recorded in the Sample and **must not be cited as verified
    quantities** in the paper. Independent verification of Artifact exposure,
    if ever wanted, is a new experiment with a new oracle — not this section
    retained as a placeholder.

21. **Require strict member-level OutcomeSet semantics for Scale exact
    candidates.** (Taken 2026-08-11 by author wuminmin after reviewing the
    OUTCOME-scope findings; this changes binding/finalizer acceptance semantics
    and approves no generated binding, measurement, capability, release, or
    tag.) For every Scale exact candidate, the evaluation-only pre-run oracle
    must independently construct the ordinary-set identity of all five expected
    Fact members: the four predicate atoms and the signed composite. The
    finalizer must reconstruct the actual ordinary set from the four actual
    atoms already prepared for validation plus the signed actual composite, and
    compare it member-for-member with the independent expectation. The
    production radix `OutcomeSetSHA256` is a different digest domain and cannot
    be compared directly with the ordinary-set oracle digest. Production output
    may supply only the actual comparison operands; it must never become the
    source of the expected members.

    The decision is required because the current Scale finalizer stops at the
    three dependency identities and their cardinalities
    (`evaluation/internal/experiment/finalize_scale_artifact.go:183` and
    `:191`). `ScaleVerificationEvidence` has expected dependency/result fields
    but no expected Outcome cardinality or observed-member summary
    (`evaluation/internal/experiment/types.go:597`). On the Outcome side,
    `evaluation/internal/experiment/finalize.go:1488` only checks that Gateway,
    receipt, and Sample repeat the same production exposure fields, while
    `internal/queryreceipt/queryreceipt.go:282` requires only
    `actualOutcome = atomCount + 1`; neither requires exactly four atoms nor
    validates the identities of the five members. Consequently an entire
    five-member set can be wrong while Gateway, receipt, Sample, radix digest,
    and shared finalizer derivations remain mutually consistent.

    The in-progress E1 aggregate called `OutcomeIdentity`, explicitly marked
    `ProductionV5OutcomeSet=false`
    (`evaluation/internal/finalv5publication/generate.go:94` and `:472`), is a
    binding-input aggregation and is not the independent five-member Outcome
    candidate set. It must not be named or serialized as
    `OutcomeCandidateSetSHA256`; if retained, it must use a name that cannot be
    read as verified Outcome membership. Timing constraint: because this
    decision changes binding/finalizer acceptance semantics, it must be fully
    implemented before the v1.5 freeze and before any P5 measurement. If strict
    member identity could not be implemented, the honest paper boundary would
    be to leave it unverified; an aggregate identity must never be substituted.

25. **Raise the Gateway HOT artifact limit to 1024 MiB so the master Catalog can

    publication must still join the master Catalog: baseline S4 binds

    existing one, and a second raise costs a full contract freeze, another
    author signature and another tag, while the difference between 512 and 1024
    costs nothing to implement.
