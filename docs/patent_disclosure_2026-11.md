## 一、发明名称（建议）

一种面向 AI agent 的企业数据访问授权方法、网关及系统：由主体属性推出可申请范围与审批链，覆盖即复用，按岗位预配。

## 二、技术领域

企业数据治理与访问控制；AI agent（通过 MCP 等工具协议调用数据接口的大模型代理）访问企业结构化报表与非结构化文档的授权、审批与审计。

## 三、背景技术与现有做法的不足

现有做法大致三类：

1. **基于角色或属性的访问控制（RBAC/ABAC）**：按角色或属性静态决定「能读什么」，没有「为了什么目的、读多久、读多少」的任务边界；agent 拿到的是与人相同的长期权限，一旦被诱导就可以无限制取数。
2. **逐次审批的数据申请流程（OA/工单）**：每次取数由人发起、人审批；agent 场景下 agent 每问一次就要人提交一次、等一次，审批人看到的是 agent 写的范围，审批疲劳且不可复现。
3. **任务级授权网关（本申请人在先论文的做法，仅作背景）**：一次人工审批编译成签名、限额、可审计的会话，审批人只能缩小不能放大，委托只收窄、全家共用一本账。该做法把「审批之后」的事做严了，但「审批之前」仍留下三个空白：
   - 谁来批、要几层，是人工指定的，没有从组织关系与数据密级自动推出；
   - 已经批过的权限，agent 再次申请时仍会生成新的待批任务，人工确认的次数随 agent 的提问次数线性增长；
   - 员工按岗位本来就该有的权限（本部门制度、本人考勤工资、分管部门经营数据）没有预配机制，入职后每一样都要申请。

## 四、发明内容

### 4.1 要解决的技术问题

在保持「任务级、只收窄、可审计」授权模型不变的前提下：
(a) 由主体属性与数据范围自动推出可申请范围与审批链，审批层数随密级升级、在申请人职权内的层自动删去；
(b) agent 的申请若已被申请人名下生效中的授权完全覆盖，直接返回该授权，不再生成待批任务；
(c) 管理员按岗位预配常备权限与年度项目，使新入职员工的 agent 入职即可查询，且与 (b) 合用后无需员工再次确认。

### 4.2 技术方案总述

系统由三部分组成：**目录（Catalog）**声明数据产品、范围维度（含有序维度）、预算档、审批路由与委托块；**网关**接收 agent 的工具调用，判定资格、规划审批链、签发授权、执行查询并记账；**审批端（OA）**只承担「人点一次批准/缩小/拒绝」。主体以属性表描述：部门、岗位族、密级包络、所在中心、本人工号、职权部门、职权中心、分管部门、跨部门资格等。

流程（图 1、图 2）：

1. agent 以申请人令牌调用 `request_data_task`，给出目的、数据产品、列、范围（部门、密级、中心、工号等）、可选预算档。
2. **有序维度向下补全**：目录对某维度声明顺序（如密级 public < internal < secret < confidential < top_secret），申请只写最高一级，网关把低于它的各级补进范围（响应返回 `scope_closure`），放行判定不变。
3. **可申请范围判定**：按申请人属性推出每个产品的可申请范围（部门来自所属部门并按跨部门资格放宽，密级来自密级包络，中心与工号默认本人并按岗位放宽）；越界当场拒绝（NOT_ELIGIBLE），不生成待批任务。
4. **覆盖即复用（新）**：若申请人名下存在生效中、未到期、仍可查询的任务，其授权在产品、列、每个点名范围维度（补全后）上都覆盖本次申请，则直接返回该任务（标记 `reused_existing_task`，附说明），不建任务、不建审批草稿，记一条审计事件；多张覆盖取到期最晚者；带父任务、委托、代开、下载的申请不复用。
5. **审批链规划（新）**：按常规排法（申请人所在部门的审批人，再各被申请部门的审批人，再按范围内最高密级触发的升级层：部门主任层、分管副总层、总经理层，同一人只出现一次），再套用三条通用规则：
   - 个人记录自助：申请的工号恰为本人 → 本人确认；
   - 职权层级：申请全在申请人职权部门/中心内且所需最高层不高于本人 → 本人确认；否则本部门一侧由高于本人的最近一层代替，其他部门照常排；
   - 数据管家：只含管家类产品（个人记录）的任务，范围中不归申请人管的部门改由管家部门审批。
   链删空即本人确认（`self_service`）。
6. **agent 提交、人只审批**：任务创建即待审批（审批端未按待审批建草稿则拒建任务），人只做批准、缩小后批准或拒绝；任一级缩小后网关按缩小后的范围重算剩余环节；最后一级批准时签发授权，有效期从那一刻起算；待批超时自动归档。
7. **项目与子任务**：申请时选长期预算档即为项目；项目下可开子任务（范围只能更窄、到期不晚于项目、曝光额度共用）；子任务由负责人本人确认，或委托给成员时由成员本人确认且资格按成员判定；撤销根任务级联归档子任务。
8. **管理员代开（个人看板）**：部门管理员或主任用 `issue_data_authorization` 替本部门员工开长期授权，任务挂员工名下，链从开单人部门起排，范围含其他部门即拒；链上出现本人即拒（申请人不能批自己的申请）。
9. **按岗位预配（新）**：以 8 与普通申请为原语，按花名册为每个主体预配：员工三张（本部门制度、本人考勤请假差旅、本人工资条），中心主任加本中心成员考勤统计，主任/管理员/副总/总经理各一个年度经营分析项目（月度 KPI 与预算执行）；管理员自己的与主任/副总的高密级项由本人申请自确认；已被本人在办项目覆盖者不另立。与 4 合用后，agent 收到「查我的考勤」「看我分管部门的 KPI」直接得到可查询的任务。
10. **一个 agent、一把令牌、身份由人切换**：网关内保存令牌摘要到主体的绑定与切换历史，只有审批端以签名请求能切换，agent 没有切换工具；每个结果附 `acting_as`，`whoami` 返回当前主体与姓名、岗位、工号。

### 4.3 各机制的要点（与素材页编号对应）

| 素材编号 | 机制 | 关键判定 |
|---|---|---|
| 1 | 审批链按密级分层升级 | 目录 `escalations`：每层 role/label/scope/values/level；触发值按字节序；同一人只出现一次 |
| 5 | 三条通用规则 | `personal_scope`、`authority_departments`/`authority_center` + level、`steward_department`；链删空即 `self_service` |
| 2、6 | 子任务本人确认 / 成员确认 | `child_self_confirm`；`member_confirm`：审批人为受托成员，资格按成员判，人类主体仍是负责人 |
| 3 | 管理员代开 | 任务挂员工名下；开单人为链首；范围仅限开单人部门；链上含本人即拒 |
| 7 | agent 提交、人只审批 | 建任务即待审批；审批端未建待审批草稿则 APPROVAL_UNAVAILABLE 不建任务 |
| 8 | 一把令牌、人切身份 | 令牌摘要→主体绑定表 + 切换历史；签名切换；`whoami`、`acting_as` |

| 10 | 撤销级联 | 根任务撤销→子任务归档（记账，不改安全判定） |
| 11 | 覆盖即复用 | 产品⊆、列⊆、每个点名维度补全后⊆、未到期、仍可查；取到期最晚；子任务/委托/代开/下载除外；审计 TASK_REQUEST_REUSED_EXISTING |
| 12 | 按岗位预配 | 花名册驱动；先撤旧再建新以免被复用吞掉；被本人项目覆盖者不另立 |

### 4.4 有益效果（均为实跑观察，不作保证性断言）

- 审批链由属性与范围推出：同一套规则在 124 人、12 部门、五级密级的演示组织上推出全部场景（员工本人记录自确认；中心主任统计本中心自确认、统计全部门由管理员批；管理员统计工资条由副总批；HR 统计全公司考勤自确认；跨部门项目多级链），换花名册时一行规则未改。
- 覆盖即复用后，副总经理问「看我分管部门今年的月度 KPI」由「建单 + 本人在 OA 确认 + 等待」变为一次调用直接可查（任务数不变）；更宽的申请仍照常建单走链。
- 按岗位预配后，新入职员工的 agent 入职当天即可读本部门制度、查本人考勤与工资条，124 人人手三张，28 名领导各一个年度经营分析项目。
- 以上均在「只收窄、全家一本账、每次查询有回执」的既有模型内完成，正式评测配置不启用这些开关时行为逐字节不变（目录 SHA 与冻结件零 diff）。

## 五、具体实施方式（结合演示组织「大米集团」）

### 5.1 目录与属性

- 范围维度：`kb_department`（12 个部门代码）、`classification`（五级，声明 `order`）、`center`（24 个中心代码）、`employee_id`（124 个登录名）。
- 数据产品：制度文档（分块与文档两张关系，节级密级，文档密级取最高节）；六张报表（月度 KPI 内部级、预算执行秘密级、工资条机密级、差旅/请假/考勤内部级；个人记录类声明 `steward_department: hr`，范围需写全部门、密级、中心、工号）。
- 预算档：`kb-large-v1`（24 小时）、`kb-annual-v1`（一年）；两档额度相同，只差有效期。
- 主体属性示例（周雨，财务部会计核算中心会计）：department [finance]、job_family [staff]、clearance [public, internal, secret]、center [finance-a]、employee_id [zhouyu]、payslip_access [hr]、display_name、title、employee_no。管理员加 authority_departments 与 request_reach；中心主任加 authority_center；副总加 oversees（四个部门）；总经理 oversees 全部。

### 5.2 审批链推导示例

- 周雨申请财务部内部制度：常规链 = [财务部管理员 黄玉梅]；职权规则不删步（员工无职权）→ 黄玉梅批。
- 周雨申请财务部秘密级：常规链 = [黄玉梅] + 主任层 [王志勇] → 两级。
- 张桂兰（业务线副总）申请分管四部门 KPI：常规链含四个部门的管理员与主任层；全部在其 oversees 内且所需最高层不高于副总 → 全部删去 → 本人确认。
- 黄玉梅申请财务部 + 销售部文档：本部门一侧由上一层（主任 王志勇）代替，销售部照常 [李海波] → [王志勇, 李海波]。
- 张丽娟（HR 管理员）申请全公司考勤：只含管家产品，非职权部门改由 HR 审批，HR 本人即申请人 → 本人确认。
- 于媛（中心主任）申请工程 + 采购：无跨部门资格 → NOT_ELIGIBLE，不生成草稿。
- 管理员给自己开个人看板：链首为本人 → APPROVER_NOT_AUTHORIZED；改由本人申请自确认。

### 5.3 覆盖即复用的判定步骤

输入：申请人、产品列表、每产品列列表、范围（已补全）。
1. 分页取申请人 ACTIVE 任务；跳过下载类任务；跳过目录版本或目录 SHA 与当前不一致、授权回执验签失败、家族链或委托链失效、视图绑定非 ACTIVE、已到期的任务。
2. 对每个候选：申请的每个产品都在授权产品内，且每列都在该产品的批准列内；对申请点名的每个维度，授权值集 ⊇ 申请值集（枚举维度按集合，日期维度按区间，授权未限制的维度视为无限制；授权限制了而申请未写的、且该产品发布或强制该维度的 → 不覆盖）。
3. 多个候选取到期最晚者，同时到期取 id 最小者。
4. 命中则以正常响应形态返回该任务（审批链为空，`budget_source = reused_existing_task`，预算与范围来自签名授权核心），写审计事件 TASK_REQUEST_REUSED_EXISTING（含申请目的、复用任务 id、申请的产品/列/范围、补全值、授权到期）。
5. 未命中则按常规流程建任务。
排除：带 parent_task_id、delegate_principal_id、代开、带下载保留范围的申请。

### 5.4 按岗位预配的编排

- 每人：由本部门管理员以 `issue_data_authorization` 开三张（制度内部级；考勤+请假+差旅内部级；工资条机密级）；工资条链为管理员 → 主任 → 副总。
- 管理员本人、主任与副总的工资条：链上出现本人 → 由本人 `request_data_task` 自确认开通。
- 中心主任：本人申请本中心四人的考勤统计（authority_center 内，自确认）。
- 主任/管理员/副总/总经理：本人申请年度经营分析项目（月度 KPI + 预算执行，秘密级，一年）；已有在办项目完全覆盖者（如财务部管理员的年度预算编制项目）不另立。
- 转换顺序：先撤销旧任务再申请新任务，否则新申请被旧任务复用。
- 结果：控制库 ACTIVE 约 440 张任务；agent 以任何岗位询问常规数据均直接复用。

### 5.5 审批端与 agent 身份

- 审批端只有一个口令，登录后两张身份卡：左卡「OA 角色切换」（以谁的名义审批）、右卡「MCP 角色切换」（共用令牌代表谁），两卡同一棵组织树（公司→条线→部门→中心→人），可搜索。
- 网关每次调用重新认证，切换即时生效；切换历史记录谁、何时、从谁切到谁。
- 审批页只显示范围（部门、密级、中心、工号、产品、字段、预算、期限），不显示数据；等待时按版本号轮询、有变化且用户空闲时才刷新。

## 八、权利要求建议骨架（措辞由代理人定）

1. 一种面向 AI agent 的企业数据访问授权方法，其特征在于：接收 agent 以申请人令牌发出的数据访问申请（目的、数据产品、列、范围）；依据目录中声明的有序范围维度把申请范围向下补全；依据申请人的主体属性推出每个数据产品的可申请范围并拒绝越界申请；在申请人名下查找生效中且授权在产品、列与每个范围维度上均覆盖该申请的任务，命中时直接返回该任务并记录审计事件而不生成新任务；未命中时依据申请范围与申请人属性推出审批链，其中按范围内最高密级逐层加入升级审批层、删去申请人职权内的审批层、把管家类产品中不属于申请人职权的部门改由管家部门审批，链为空时由申请人本人确认；由人逐级批准或缩小后批准，最后一级批准时签发只收窄的签名授权。
2. 根据 1，所述查找排除带父任务、委托对象、代开对象或下载保留范围的申请，并在多个覆盖任务中选择到期最晚者。

4. 根据 1，审批链中同一审批人只出现一次；审批人缩小范围后按缩小后的范围重新推出剩余审批层。
